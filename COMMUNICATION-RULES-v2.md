# Communication Rules — SA Daily Lotto Project

## Session Rules (Binding)

1. **Exact execution only** — Do exactly what is requested. No additions, no improvements, no assumptions beyond what is asked.
2. **Present before proceeding** — State the request back to the user before taking any action. Wait for confirmation is implied by the rule; act only after presenting.
3. **Clear** — No vague language. State exactly what was done, found, or needed.
4. **Brief** — No padding, no preamble, no trailing summaries. Say it once.
5. **Summarised** — Compress findings to their essential point. No walls of text.
6. **Only positive, research-enhancing findings** — Share only news that adds real value to the project's research. Nothing else gets surfaced alongside it — no null-result framing, no "it's just noise" commentary, no negative-only findings presented as the headline.

## Work Rules (Binding)

7. **Never skim read** — Read every file fully before acting on it.
8. **Never assume** — If it is not confirmed in the file or output, it is not known.
9. **Never guess** — No inferences presented as facts.
10. **Always audit and confirm before touching anything** — Verify state first, act second.
11. **Do what the user wants** — Not what seems logical, not what seems better. What is asked.
12. **Ask when unclear** — One direct question. No proceeding blind.
13. **Before writing anything — plan first** — Think through the approach before producing any output.
14. **Facts only — no fantasy** — Every number, window, and conclusion must come from independent analysis of the raw data. Never copy figures from reference documents and present them as findings. Reference files are context only, not a source of truth.
15. **Phase task list before implementation** — When assigned any work, first create a named phase task list of every item to be done, then implement each item in order. No implementation starts before the full list is written.
16. **Read context, plan the method, then execute** — We are two different entities. Read and fully understand the context and intent before choosing a method. Plan which approach produces the simplest yet most effective result. Do not execute the first method that comes to mind. Think it through first.
17. **Individualistic before generalistic** — Never test by pooling or averaging across all cases as the primary method; the aggregate washes real signal out into apparent noise. Test each unit (anchor · triple · window · number · system) INDIVIDUALLY first, record each one's own signature, THEN generalise from the collection of individual findings. The average is the LAST step, not the first. If a pooled test reads "flat / random", re-run it per-unit before concluding no signal exists. (Proven 2026-07-06: pooling every Wide-30 3-hit triple's completions read as "no signal, 3→5 not driftable"; mapping all 223 triples one-by-one surfaced real per-triple zone-drift — e.g. `(1,2,11)` completes 86% up into zones B/C; `(4,25,27)` lands 88% in zone B.)
